## 2026-10-20, Google sign-in uses the backend-driven authorization code flow (PKCE) with redirects
- **Decision:** feature 1 signs users in with `GET /auth/google/start/` and `GET /auth/google/callback/` (code + PKCE, server-side code exchange, signed `SameSite=Lax` state cookie). No Google JavaScript, iframe, popup or One Tap. This replaces the earlier plan of the frontend sending an ID token to `POST /auth/google/`.
- **Reason:** the previous project's Google button did not work in some browsers; its code ended on a full-page `form_post` redirect to avoid blockers and iframes. That flow still needs a `SameSite=None; Secure` cookie for a cross-site POST, which Safari rejects on `http://localhost`. A GET callback works with a Lax cookie in every browser and needs no third-party cookies. The failure causes are inferred from that code and its comments, not from a bug report.
- **Alternatives:** Google Identity Services button/popup (rejected: the failures above); implicit `form_post` redirect as before (rejected: SameSite=None cookie); frontend-held ID token (rejected: needs the GIS script).
- **Files:** `backend/Project.MD`, `backend/docs/GOOGLE_OAUTH_SETUP.md`, `backend/README.md`.

## 2026-10-20, Feature 1 uses django-allauth (supersedes the hand-written Google flow and the earlier "allauth dropped" entry)
- **Decision:** accounts use `django-allauth[socialaccount]`: Google provider (code flow, PKCE, state, account linking by `sub`) and `allauth.usersessions` (device session list and revoke). We write the `User` model (no password, UUIDv7), a social-account adapter (rules, redirects), our own JSON endpoints in the response envelope for sessions and profile, and account deletion with a 7-day grace. Google `sub` is read from `SocialAccount.uid`, not stored on `User`. Only the Google provider URLs are mounted; allauth's password/signup/HTML pages and headless API are not exposed. The redirect URI becomes `/api/auth/google/login/callback/`.
- **Reason:** the owner asked why allauth was not used. It covers the OAuth flow, sessions list and remember-me with maintained code, so we avoid hand-writing and securing them. The browser-compatibility reasoning is unchanged: allauth's flow is a full-page redirect with a GET callback and a Lax session cookie, with no Google script, iframe or popup.
- **Alternatives:** hand-written flow (earlier plan; rejected as more code to maintain), allauth headless API (rejected: its responses do not use our envelope and it adds surface we do not need).
- **Files:** `backend/Project.MD`, `backend/docs/GOOGLE_OAUTH_SETUP.md`.

## 2026-10-20, Throttling of the Google sign-in endpoints
- **Decision:** allauth 65.20.0 rate-limits only its account views (`ACCOUNT_RATE_LIMITS`); its Google provider and usersessions code have none. Our `start` view and a wrapper around allauth's callback use `common.throttling.scoped` (`AnonThrottle` + `AuthScopedThrottle`, scope `google`, 20/min per IP), and throttled requests redirect to `/login?google_error=rate_limited`. JSON endpoints use the default throttles, with a stricter `account_delete` scope.
- **Reason:** owner asked what rate limiting allauth provides for feature 1; one throttling mechanism for the whole API is easier to configure and test than mixing allauth's limiter in.
- **Files:** `backend/Project.MD`.

## 2026-10-20, Feature 1 built: allauth settings, verified behaviour and deviations
- **Decision:** `accounts` app implemented on django-allauth 65.20.0 (installed with `django-allauth[socialaccount]`). Owner answers: env names use the `RESOLVE_AI_` set, redirects use `RESOLVE_AI_FRONTEND_URL`, sessions last 14 days (30 with remember me), signing in during the grace period cancels deletion, an audit hook exists now, `SessionMeta` only if needed, dependency approved.
- **Verified against allauth 65.20.0 ("verify" items):** `UserSession` has `created_at` and `last_seen_at` but no remember-me flag. The flag is not needed by the API, so `SessionMeta` was **not** added. `UserSession.pk` is an integer, so session ids in the API are integers scoped to the owner (other users get 404). Only the Google callback and a start view are mounted; allauth's own account URLs and `google/login/token/` are not routable. The OAuth redirect URI is built from the request host (`reverse("google_callback")`), so `PUBLIC_API_URL` is only a documented setting; the proxy must preserve `Host` and send `X-Forwarded-Proto`.
- **Deviations from Project.MD:** (1) later logins refresh `avatar_url` only; `display_name` is filled on first login and not overwritten, so a name chosen with `PATCH /me/` survives. (2) `SESSION_SAVE_EVERY_REQUEST = True` so the session lifetime is really sliding as documented. (3) `User` also has `is_staff` (Django admin needs it). (4) The log middleware now redacts cookies, `X-CSRFToken`, `id_token` and the `code`/`state` query values, because the OAuth callback URL carries a single-use code and the session cookie was being logged.
- **Reason:** keep one throttling mechanism and the response envelope; never let an OAuth code, session id or token reach logs or responses.
- **Alternatives:** allauth headless API and its HTML pages (rejected, as before); a `SessionMeta` table (not needed).
- **Files:** `accounts/**`, `config/settings.py`, `config/urls.py`, `common/logger/*`, `pyproject.toml`, `uv.lock`, `postman/*`, `README.md`, `../README.md`, `FLOW.md`, `Project.MD`.

## 2026-10-20, Feature 6 built: Gmail through the single sign-in flow
- **Decision:** `email_integration` app implemented (details in `Project.MD`, Feature 6). Owner decisions: one flow only, Gmail scopes (`gmail.send`, `gmail.readonly`, offline access) are requested at Google sign-in and no "Connect Gmail" flow or second callback exists; unrelated mail is never stored; the manual sync reads at most the newest 30 inbox messages; the review list keeps the newest 30 per user for 30 days; unmatched mail is only kept when the sender is a known customer. - **Choices I made (change on request):** declining the Gmail permission still lets the user sign in (status `not_connected`, with a `reconnect_path`); Google sends a refresh token only on first consent, so `?reconnect=1` forces `prompt=consent` (also for signed-in users, which also fixed the signed-in shortcut of `/auth/google/start/` that DRF's anonymous user had disabled); granted scopes are read from Google's `tokeninfo`; the Gmail REST API is called with `requests` instead of adding google-api-python-client; a reply is matched by headers *and* the sender must be the ticket's customer; the portal confirmation is stored as a `system` message so replies to it thread; replies go out from the sending agent's own mailbox with the Gmail thread id of that mailbox; temporary errors retry 3 times; no automatic retry of permanent failures, agents use "resend"; the first push/sync only records the starting history position (no backfill); Pub/Sub pushes must carry a Google-signed JWT for the configured audience and service account; `config/__init__.py` now loads the Celery app so tasks run (eagerly in tests).

## 2026-10-22, Context search for tickets and chat (steps 2 to 14 of the context plan)
- **Decision:** given a ticket (subject and description), one public customer message, or a chat question, return the best passages from PUBLISHED articles of the same workspace, with citations. Tickets themselves are never searched. **Files:** `common/search/`, `common/llm/`, `ai/`, `knowledge/services/{chunker,chunk_service,context_service}.py`, `tickets/services/context_service.py`.
- **Search:** Postgres full-text only (no embeddings, no reranker). Articles are split into chunks (Markdown headings of level 1 to 3, then paragraphs of about 600 to 1,200 characters, code blocks whole) with a GIN-indexed `tsvector`. One language per workspace (`Workspace.search_language`, 14 whitelisted configs, default `english`); changing it reindexes in Celery. The query is a raw OR `tsquery` of stemmed terms (12-term cap, longest first), ranked with `ts_rank_cd` (weights 0.1/0.2/0.4/1.0, normalization 32). Passages below 0.05 (up to 2 terms) or 0.3 (3 or more) are dropped. **Reason:** an AND query finds nothing for a long customer message; the score floor removes single-common-word noise. `ts_headline` snippets (markers `⟦ ⟧`) are made only for the returned rows.
- **Rewriting:** the LLM writes 3 variations; the original and the variations are searched separately and merged with reciprocal rank fusion (1 / (60 + rank)), top 5 (since 2026-10-23 there is no per-article limit). Rewriting is always attempted but any failure (no key, allowance spent, timeout, provider error, bad output) falls back to the original text and the response says `rewritten: false`. Rewrites are cached for 1 hour per workspace and text.
- **Articles in the database:** `KnowledgeArticle.content` (100 KB cap, at most 100 articles per workspace) replaces R2 storage for article bodies so chunks can be rebuilt in the same transaction; uploaded files stay in R2. `size_bytes` still counts toward the 50 MB quota.
- **LLM layer:** strategy pattern in `common/llm/` (Gemini and OpenAI through their official SDKs, a fake for tests), one entry point `ai/services/llm_service.generate`. 30 s timeout for both, SDK retries off. Models are allowlists in `common/llm/constants.py`; Resolve AI's own key serves only `gemini-3.5-flash-lite` (default) and `gemini-3.1-flash-lite`. The OpenAI model names come from my knowledge, not a live list; check them before relying on them.
- **Per-user settings (one key per provider):** `UserWorkspaceLLMSettings` per (user, workspace) holds the mode (Resolve AI or own key), the Resolve AI model and `active_provider`; `UserWorkspaceLLMKey` holds one saved key per (user, workspace, provider) with its model. Gemini and OpenAI can each have a key; the active one answers. Adding the first key makes it active; deleting the active key hands over to the next one, or returns to Resolve AI. Each key is Fernet-encrypted and bound to workspace and user, validated with a real call on save, never returned (only the last 4 characters), and deleted when the member leaves or is removed. Endpoints `GET/PATCH /api/workspaces/{id}/llm/`, `PUT/DELETE .../llm/keys/{provider}/` (replaces `.../llm/key/`). Migration `ai.0002` copies existing keys; run `migrate`.

Throttle scope `ai`, 30 per minute per user.

## 2026-10-23, RAG over uploaded documents (hybrid search with embeddings)
- **Decisions taken by the user:** (1) Search is hybrid: Postgres full-text plus pgvector embeddings, over chunks of BOTH published articles and uploaded documents, in the one `knowledge_chunk` table. (2) Embeddings for articles and uploads, one fixed server-side Gemini model (`gemini-embedding-001`, 768 dimensions) on the existing `RESOLVE_AI_GEMINI_API_KEY`. (3) LLM call 1 rewrites the question into 3 short queries; the original and each rewrite are searched by words and by meaning; the ranked lists are merged with reciprocal rank fusion (no LLM); LLM call 2 writes the answer from the top passages with `[n]` citations. (4) Uploads: PDF, DOCX, MD, TXT (no legacy .doc), 10 MB per file, 50 MB per workspace. (5) Reading files: pdfplumber and python-docx as an in-process Python dependency, no secondary service; its models are baked into the Docker image; OCR is pdfplumber and python-docx's bundled RapidOCR. Follow-up chat turns are still out of scope.
- **How it works:** confirming an upload queues `knowledge.index_upload` on the default queue: pdfplumber (PDF) and python-docx (DOCX) turn the file into Markdown (per page for PDFs, 300 s and 100 pages at most), the Markdown is stored beside the file, split into passages by heading (long paragraphs and tables are cut with a small overlap; the heading path and PDF page are kept) and written to `knowledge_chunk` with `upload_id` set (exactly one of `article_id` and `upload_id`, enforced by a check constraint). `index_status` is pending, indexing, indexed or failed; `index_error` holds a code such as `document_corrupt`, `document_empty`, `document_timeout`. Re-reading keeps passages that did not change, so their embeddings are kept. A sweeper (every 10 minutes) re-queues uploads whose message was lost or whose worker died. Whenever new passages are written (article save or upload indexed), `knowledge.embed_source` embeds them after the transaction commits (batches of 100, 3 retries), and a sweeper (every 15 minutes) embeds anything still missing or made by another model. Chunks without a vector are still found by words.
- **Search:** `context_service.retrieve_context`: rewrite (cached 1 h) -> the original and rewrites embedded in ONE request -> per query a word search (top 20, score floor) and a vector search (top 20, cosine similarity at least 0.55, HNSW index with pgvector's iterative scan so the workspace filter cannot starve the result) -> RRF (k = 60) -> top 5 (no limit per article or file: the owner decided on 2026-10-23 that a document that holds the answer should fill the results; the cost is that one file can crowd out others). Fallbacks: rewriting fails: the original text; embedding fails or no key: words only; no word match: the vector search decides. SQLite (tests) searches by words only. A result has `source` {type, id, title, page}; `article` is kept for article passages and is null for files. `ask/` also returns `answered`; the prompt now says "articles and uploaded documents" and labels each excerpt with its heading path and page.
- **Limits:** embedding uses the Resolve AI key whatever mode the user chose, so it has its own limits, separate from the 100 daily rewrite/answer calls: 20,000 embedded chunks per workspace per UTC day (`EMBED_DAILY_CHUNK_LIMIT`; chunks over it wait for the next day's sweep) and 300 searches per user per workspace per day for query embeddings (`EMBED_QUERY_DAILY_LIMIT`; over it, searches fall back to words only). A user's question text is therefore sent to Google for embedding even with their own key; the Settings notice says so.

## 2026-10-27, BM25 word search with ParadeDB (RAG upgrade, step A)
- **Decision:** the Postgres image changes from `pgvector/pgvector:pg17` to `paradedb/paradedb:0.25.6-pg17`, and the word search ranks with BM25 from a `pg_search` index instead of `ts_rank_cd`. The user approved the switch ("a learning project with no real users"), which supersedes the guide's "no ParadeDB" scope line.
- **How:** `KnowledgeChunk.bm25_terms` holds the stemmed words of `search_vector`, one per occurrence, heading (weight A) words repeated `BM25_HEADING_BOOST` (2) times; `chunk_service.fill_vectors` fills it with the search vector. The BM25 index `knowledge_chunk_bm25_idx` (`USING bm25 (id, bm25_terms) WITH (key_field = 'id')`; pg_search 0.25.6 requires `key_field`) is created by migration `0012_chunk_bm25`, which also backfills. `context_service._bm25_ranked` queries it with the same stemmed lexemes `context_query` already builds (`bm25_terms ||| 'a b c'`, `pdb.score`), filtered to the workspace and to published articles / ready uploads. Indexing lexemes instead of raw text keeps per-workspace language stemming and stop words (one tokenizer config could not).
- **Fallback:** if the query raises `DatabaseError` (no `pg_search`, a plain Postgres), `_ranked` falls back to the old tsvector search. The migration skips the index when `pg_search` is not available. SQLite tests are unchanged.
- **Choices I made (change on request):** no score floor (BM25 scores depend on corpus size). Instead a passage must contain the query's words `CONTEXT_BM25_MIN_HITS` (1) times, or `..._MANY_TERMS` (2) when the query has 3+ words, which keeps the old rule that one stray body word is noise but a heading word counts. The query reads `CONTEXT_BM25_POOL` (100) rows from the index (workspace filter only, no joins), then drops drafts/archived ones in Django. IDF is corpus-wide (all workspaces share the one index), so another workspace's documents can nudge scores but never appear in results; accepted for a learning project. No candidate pool or Redis stats cache: the index computes BM25 itself.
- **API note:** `score` in the context/ask results is now a BM25 score (not capped at 1) whenever the BM25 index answered; the frontend only types it and does not show it. BM25 statistics also count rows from rolled-back transactions until ParadeDB merges/vacuums, so two close passages can swap order in a long test run; the ranking test checks presence, not exact order.

USING bm25` and `|||` / `pdb.score` SQL and the three `pg_search` tests were NOT run (they skip without the extension). The `bm25_terms` SQL was checked on plain Postgres 16. pgvector's presence in the ParadeDB image and the 0.25.6 syntax need a real run.
